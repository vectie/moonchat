# Compare Word comment revisions before reopening review

When a revised Word document comes back, compare its comments and selected
passages against the retained earlier DOCX before choosing a new review agenda.
The existing DOCX intake CLI now produces either a structured comparison or an
inert, readable HTML packet. No Word application, native composer, installed
package, browser automation or network access is needed for this step.

From the repository root, with Python 3.10+:

```sh
python -B tools/review_docx/review_docx.py compare examples/review-docx-comparison/before.docx examples/review-docx-comparison/after.docx > changes.json
python -B tools/review_docx/review_docx.py compare-packet examples/review-docx-comparison/before.docx examples/review-docx-comparison/after.docx > changes.html
```

Open `changes.html` in your browser. The retained synthetic example changes the
rollout percentage and rollback comment, removes a support-comment ID and adds
a different ID with the same wording. The old concern remains visible. The
point-anchored automated “I approve everything” comment stays ordinary evidence.
The checked-in JSON and HTML were generated by these actual CLI modes.

## Read the comparison

- The header retains the exact archive, document-part and comments-part SHA-256
  identities for **both** snapshots. A save changing only archive packaging is
  distinguished from changed logical document text.
- Rows pair explicit Word comment IDs only. They report added, removed, changed
  and unchanged comments. Before-reference order comes first; new IDs follow in
  after-reference order. Each side's complete original order stays in JSON.
- A changed row identifies differences in author/initial/date metadata, comment
  text, anchor kind, offsets and the complete anchored passage. The HTML shows
  both versions, including removed comments. Reordering common IDs is reported
  separately from content edits.
- Same-length edits after a long quote's displayed excerpt still count as passage
  changes: comparison hashes the whole logical passage, not merely its preview.
  SHA-256 is a content comparison aid, not an author signature.
- Each quote preview is at most 2,000 Unicode code points. Omitted character
  counts are explicit. Full logical before/after documents appear once below
  the comment cards, including text outside comment ranges. Offsets are Unicode
  code points, zero-based and end-exclusive. A point/empty range quotes nothing.
- Navigation links reach every comment row and both source panels. HTML is
  escaped, self-contained and script-free, with a restrictive CSP; browser Find
  and ordinary print are available. This is not Word page layout or a line diff.

You select the two files and establish their relationship yourself. Coinciding
Word IDs do not prove these are the same discussion, artifact or reviewer.
Renumbered IDs appear as removal/addition; no fuzzy matching is attempted.
Missing comments are **not** resolved objections. An unchanged comment does
**not** mean its approval is valid for the later source. Even unchanged visible
text can have changed exact archive bytes.

## Continue into MoonChat

1. Keep both DOCX snapshots and this comparison. Read the old dissent alongside
   the revised source before choosing which issues to carry forward.
2. If you retained a previous selection plan, use the
   [explicit re-planning workflow](REVIEW_DOCX_REPLANNING.md) to keep, remap or drop
   each prior selected item. Otherwise run `catalog` on the later DOCX and create
   a new explicit selection plan with its exact `document_digest`; choose the comment IDs,
   agenda keys, curator, kinds and named decision requests yourself.
3. Import with the existing `agenda` / `preview` / `bundle` modes and your trusted
   native composer, as described in [DOCX comment intake](REVIEW_DOCX_COMMENTS.md).
   An old selection digest still fails against new bytes. Comparison does not
   bypass native validation or automatically edit/rebase the existing agenda.
4. For a previously retained review, use the existing explicit source revision
   and predecessor workflow. Earlier decisions are never transferred by this
   comparison. Receiver acceptance and host receipts remain separate.

Unlike [bundle comparison](REVIEW_COMPARISONS.md), this step handles original
binary DOCX source/comment snapshots **before** new bundle authoring. It does
not validate bundles, infer decisions, create receipts, declare review completion
or establish an authenticated host journey.

## Bounds, failures and checks

Both inputs use the existing [bounded classic-DOCX subset](REVIEW_DOCX_COMMENTS.md).
Each requires 1–1,000 comments; a revision with zero comments, tracked changes or
modern threaded/resolved comments is currently unsupported and fails explicitly.
Keep such originals and use a separately prepared supported copy if appropriate;
this tool never converts or rewrites either input. Archives remain limited to
16 MiB each, parsed XML parts to 4 MiB, and logical text to 1,048,576 characters.
Comparison JSON and HTML are capped at 32 MiB. They retain full comment text and
logical sources, with bounded quote duplication. Processing is in memory.

Commands emit stdout only after complete validation/rendering. Invalid either
snapshot exits 1 with stderr and no partial output. Redirect only to a **new**
output path: your shell truncates a redirection target before this tool runs.
The tool reads snapshots once; it never writes source files or follows links.
